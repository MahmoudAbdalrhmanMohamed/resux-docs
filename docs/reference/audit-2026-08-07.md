## Executive summary

The framework has a broad feature surface and a strong existing CI matrix, but the audit found a repeated architectural source of bugs: several major subsystems duplicate behavior between the TypeScript/server implementation and generated browser-runtime source. That duplication has already produced parity defects in scheduling, reactivity, package loading, request identity, and runtime cleanup.

The highest-value long-term improvement is to make those shared semantics come from one implementation or one conformance suite rather than fixing two copies manually.

The documentation already covers most framework areas at a guide level, but package-surface completeness was uneven. The clearest gap was `resuxjs/ui`: more than twenty public components existed while the documentation only listed their names. A dedicated UI API reference and integration cookbook are part of this audit.

`resux-lab` is valuable but needs to become a reproducible compatibility bench rather than a developer-local demo checkout. The audit branch adds/organizes verification around public APIs and removes committed generated/accidental artifacts.

## Priority list

### P0 — correctness and safety

These were implemented or covered by framework audit PR #16:

1. **Concurrent SSR request isolation** — request-local app, error, translation, and device context must not leak between renders.
2. **Create-target symlink safety** — `--force` must refuse symlinks in the target or any existing parent component and must detect target replacement during cleanup.
3. **Concurrent Resux Kit module context** — overlapping async module setup must use request/task-local context rather than a process-global variable.
4. **Compiler path containment** — imported assets in prefix-matching sibling directories must never be treated as project-relative paths.
5. **Generated runtime parity** — property additions, scheduler behavior, native objects, `toRefs`, deep watch iteration, and lazy-package retry must match source behavior.
6. **`useFetch` request identity** — method, headers, body, and relevant request options must be part of deduplication identity; binary bodies must not expand into giant resource keys.

### P1 — documentation and verification

1. Document every `resuxjs/ui` public component and alias.
2. Provide a standard third-party integration cookbook rather than only isolated media examples.
3. Make the lab build from a fresh clone with an explicit framework-under-test workflow.
4. Add lab routes for UI primitives and browser capability integrations.
5. Keep public API/export coverage visible in the docs reference.
6. Link every new guide/reference in VitePress navigation so it is discoverable.

### P2 — architecture and DX

1. Split `src/runtime/index.ts`, `src/compiler/index.ts`, and `src/cli.ts` into smaller internal modules.
2. Eliminate hand-maintained source/generated-runtime duplication where possible.
3. Introduce one shared `isPathInside(root, target)` utility for compiler/create/output safety checks.
4. Generate a public API manifest during CI and fail when a new export has no documentation mapping.
5. Run `resux-lab` as a compatibility job against framework PR heads in addition to released/main versions.
6. Export stronger component prop types from `resuxjs/ui` so docs and editor tooling can derive contracts directly.

## Framework findings and changes

### Runtime / SSR

The audit identified and addressed:

- request-context leakage through process-global mutable app state;
- shared error state across overlapping server renders;
- translation globals that could bind to the wrong request;
- route-derived device information using shared context;
- URL-only `useFetch` deduplication;
- unbounded binary request-identity serialization;
- lazy package and CSS failures poisoning caches permanently;
- generated client package retry behavior drifting from source behavior.

### Reactivity

The audit identified and addressed:

- recursively requeued jobs that could hang a flush indefinitely;
- one watcher exception aborting later queued jobs;
- plain proxy wrapping of native internal-slot objects such as `Date`, `Map`, `Set`, and `RegExp`;
- generated `toRefs()` losing array shape;
- deep watchers missing symbol keys and object add/delete iteration;
- generated property-add behavior failing when a new property is assigned `undefined`.

### Compiler / CLI

The audit identified and addressed:

- incomplete `.nuxt` to `.resux` generated-path normalization in CLI flows;
- string-prefix project containment checks (`startsWith`) that mistake sibling paths such as `/app-copy` for descendants of `/app`;
- the same containment defect in both ES imports and TypeScript `import = require(...)` asset handling.

### Core / Kit

The audit identified and addressed:

- hook arrays being iterated live while handlers can register new handlers;
- Kit context disappearing after `await`;
- the initial async fix still being process-global and therefore unsafe for overlapping async module setup;
- task-local Kit context through `AsyncLocalStorage` plus an overlapping-context regression test.

### Project creation

`--force` is intentionally destructive and therefore receives stricter path checks. The audit expands protection from only checking the final target symlink to checking every existing path component and detecting target identity changes during cleanup.

### i18n

The audit fixed canonicalization of explicit default-locale prefixes under `prefix_except_default`, duplicate locale prefixes during locale switching, and loss of browser query/hash state.

### UI

The audit fixed animation lifecycle/fallback behavior and DatePicker rendering of current/invalid values. Documentation now treats the UI package as a first-class public API instead of a component-name list.

### Release flow

The repository contains both `resuxjs` and `create-resuxjs`. Release/package verification now treats them independently so an already-published framework version cannot suppress publishing the create package.

## Integration strategy

The standard integration decision is now:

1. **SSR** for pure/Node-compatible packages.
2. **Progressive enhancement** when server HTML can exist before the library.
3. **Client-only** when a package requires browser APIs.
4. **Vue island** when the third-party package is naturally a Vue component tree.
5. **Server-only** for credentials, admin SDKs, filesystem/database clients, and privileged APIs.

The Integration Cookbook applies this model to Swiper, Google Maps, video players, PDFs, charts, date pickers, camera/media capture, file picking/uploads, browser permissions, authentication SDKs, Firebase, Supabase, Stripe, editors, markdown, syntax highlighting, and utility/animation packages.

## Breaking-improvement proposals

These are recommendations, not changes to silently ship in a patch release.

### 1. One runtime semantics source

**Problem:** source/runtime-generated duplicate implementations repeatedly drift.

**Proposal:** move portable reactivity/scheduler/package identity logic into shared implementation modules that can be bundled into the generated client runtime, or generate both from one AST/template source.

**Trade-off:** larger internal refactor and possible build-pipeline complexity, but much lower long-term correctness cost.

### 2. Stable internal packages

Split the current very large compiler/runtime/CLI files into internal packages or directories with narrow responsibilities. Keep public entry points stable while internal module boundaries improve testing and ownership.

### 3. Machine-enforced public API documentation

Generate an export manifest and map each symbol to a documentation anchor. CI should fail on an undocumented new public symbol unless explicitly marked internal/experimental.

### 4. Lab as a required compatibility gate

Run the lab against:

- framework `main`;
- the current framework PR head when one exists;
- Node `20.19.0` — the exact minimum declared by `package.json#engines` and the minimum CI compatibility selector;
- Node `22.x` — the framework compatibility selector is exactly `node-version: 22`;
- Node `24.x` for a primary-CI smoke pass — the main build/test/template/deployment jobs use exactly `node-version: 24`.

Keep this matrix synchronized with `resux/package.json#engines` and `.github/workflows/ci.yml` whenever supported Node versions change. This catches integration regressions that unit tests cannot see.

### 5. Major-version compatibility cleanup

Legacy Nuxt-named compatibility aliases/config fallbacks should remain documented and intentionally supported during the current line. If Resux wants a cleaner independent API, deprecate them with warnings and remove only in a documented major release rather than silently breaking existing apps.
